# Local verification response enumeration — recovery handoff

**Classification:** targeted implementation defect, local enabled verification only. **Authority:** AUTHORIZED — build-feature delegation (owner's verification-only request, 2026-11-11). Independent review found that Better Auth returns a generic 200 for unknown/verified addresses, while an existing unverified non-allowlisted account triggers mail refusal and a 503. This reveals account state. Historical focused checks did not exercise this comparison; no real provider send occurred. No production or user data recovery is needed.

**Targeted repair:** In the enabled local verification mode, reject non-allowlisted resend requests before any account lookup or provider/capture operation with the same generic request-received response used for allowed requests. Normalize the resend endpoint's mail-attempt failures to that generic response as well, so provider failures for the permitted address cannot expose account state. Do not state that mail was accepted or delivered. Preserve the fail-closed callback, all other routes and non-enabled behavior. Validate real-runtime known-unverified, unknown and provider failure cases have indistinguishable public response and disallowed cases make no network call. Follow with independent review and verification. No resets, production operations or broadened recipients.

**Second review and premise census:** Response equality alone was insufficient: disallowed requests bypassed Better Auth rate limiting; allowed unknown accounts took the provider’s 500 ms floor while known unverified accounts could wait up to ten seconds; all 400/429 results were hidden. The actual callback assignment causes the timing skew. The prior early-return repair is withdrawn. Route every request through Better Auth validation and rate limiting; preserve 400/429 and headers; normalize only successes and actual mail-attempt failures. Bound provider attempts to three seconds and apply a 3.5-second shared resend floor. The integration test `tests/integration/local-verification-runtime.test.ts` is the rerunnable actor census; it compares known and unknown recipients, provider call counts and timing. This reduces the bounded provider skew, not arbitrary database or network variance.

**Integration harness recovery:** The focused auth, account-email and booking-notification suites failed during import, before any tests ran, because the new server-only module entered the Node integration graph. This is a Node/Vitest resolver setup defect, not provider or database failure. Authorized repair adds the same `server-only` sentinel mock already used by individual integration tests to their shared Node-only setup; the production module guard remains in place. Re-run the affected suites and the enabled runtime test, then review the harness change.

**Fixture-state follow-up:** A repeated enabled-runtime run hit 429 after earlier test runs reused its isolated development rate-limit bucket. The scoped fixture resets only signup and verification counters through the guarded `learli_owner` connection on `127.0.0.1:55438/learli_dev` before this explicitly enabled test; application rate limits remain enabled. Re-run twice to prove repeatability.
