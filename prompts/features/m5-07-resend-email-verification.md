## Outcome and scope

In explicitly enabled ordinary local development, a verification request for the exact authorized owner address can reach the owner's inbox via Resend's permitted test sender, with the genuine Better Auth link pointing to the existing loopback app. The default remains local private capture. Password reset, both email-change proofs and booking notices remain captured locally. No hosted/production configuration, broad recipient sending, new provider, schema, payment, or other auth behavior is authorized. The address is a recipient, never a redirect or substitution: refuse a different account recipient, without transmitting that account's proof to the owner. No terminology clarification is needed.

## Evidence and constraints

- `src/lib/auth-factory.ts` composes Better Auth and routes ordinary local messages to `captureOperationalMail`; `src/features/hosted-auth/composition.ts` supplies the genuine verification callback. Local capture validates loopback proof and callback URLs.
- `src/lib/env/schema.ts` currently rejects Resend credentials in local workflow; `src/lib/email/transactional-message.ts` and `resend-transport.ts` enforce HTTPS origins and verified sender binding for hosted paths. Do not weaken these shared hosted constraints for loopback. Existing hosted transport is disabled by default, recipient-allowlisted, bounded and redacts provider errors.
- Local authentication UI explicitly promises capture (`src/features/auth/auth-form.tsx`); enabled verification delivery needs truthful, non-enumerating messaging while reset and email change retain capture instructions. Other policy text that asserts all messages are captured must stay truthful.
- Provider testing restrictions and account status are external facts; no domain or credentials are presumed. `onboarding@resend.dev` is a test sender, not a verified owned domain. A real provider acceptance is not proof of inbox arrival or link completion.

## Design and build sequence

1. Add a separate, server-only, disabled-by-default local verification configuration bound to the existing ordinary `LOCAL_WORKFLOW_MODE` capability, owned local DB and exact loopback origin. Require explicit opt-in, exact owner recipient, test sender `onboarding@resend.dev`, a valid Resend key and a fresh opaque idempotency key per one-shot request; reject partial/invalid configuration without echoing values. No credential is committed, exposed to client, or printed. Permit only this dedicated configuration; do not remove existing ambient `RESEND_API_KEY` / `EMAIL_FROM` prohibitions or allow it in test, Neon development, hosted, staging or production. Bind runtime configuration changes to auth singleton/restart semantics.
2. At the trusted mail callback route only `kind === verification` to a narrowly scoped local transport when enabled and recipient exactly matches the authorized mailbox. The actual provider callback recipient must equal the allowlist; no test-recipient override, aliases, or forwarding. Refuse other verification recipients without provider I/O; do not silently fall back to capture for them or report successful sending. All other kinds use existing `captureOperationalMail`. Keep actual provider proofs private; do not log links, addresses, credentials, raw errors or response bodies. Preserve Better Auth and existing attempt boundary behavior, returning a safe failure for rejection, timeout, or uncertain acceptance; no automatic retries or delivery claim.
3. Reuse the existing SDK transport/validated message strategy where possible with a **separate explicit local-only capability and constructor**, preserving hosted HTTPS and verified-domain guarantees. Enforce exact bound loopback origin, allowed verification path, unique token, safe callback and query constraints as in `captureOperationalMail`; ensure the transport accepts only the bound capability and verification template, rejects unbranded messages and all other origins/recipients before network. Never generalize HTTPS validation globally. If safe reuse requires invasive changes, implement a minimal isolated server-only adapter with the same bounded timeout, fixed endpoint, sanitized errors and recipient checks. Tests must exercise the actual boundary. User-facing text reports only that an eligible verification request was processed, with an accurate local instruction appropriate to the configured mode, without account enumeration or unverified delivery claims.
4. Document opt-in and teardown in `.env.example` and `docs/operations/local-workflow.md`; placeholders only, no keys or owner-specific secret in Git. Document exact-owner testing, restart requirement, the loopback link's same-machine limitation, account-matching requirement, and verified-domain gate. Update relevant canonical context if its current capture-only statements need qualification, plus `context/progress-tracker.md` with actual evidence after implementation/verification. No production environment or external billing changes.

The coordinator refined the identity mechanism: the shared HMAC constructor requires HTTPS, while this isolated adapter makes a single attempt with a random UUID and never persists or retries its identity. An additional identity secret is therefore unnecessary; shared HTTPS restrictions remain unchanged.

**Recovery refinement (2026-11-11):** Enabled verification resend requests pass through Better Auth validation and rate limiting. Successful outcomes and mail-attempt failures receive the same non-claiming response; validation and rate-limit responses retain their statuses and headers. A three-second provider deadline and 3.5-second shared response floor reduce callback-dependent timing skew in this local test, without a production constant-time guarantee. See `prompts/recovery/2026-11-11-local-verification-enumeration.md`.
