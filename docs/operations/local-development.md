# Local M2 development

Prerequisites: Node 24.20.0, npm 11.19.0 and PostgreSQL 17 command-line binaries
(`initdb`, `pg_ctl`) on PATH. On this machine PostgreSQL 17.11 is already installed.
If needed, set `PG_BIN` to the directory containing the PostgreSQL 17 binaries.

```sh
npm ci
npm run local:setup
npm run dev
```

Open `http://127.0.0.1:3000` (use this exact origin for auth). Setup creates its own
cluster under ignored `.local/postgres`, listens only on `127.0.0.1:55432`, and
creates `learli_dev` and `learli_test`. It does not modify a Homebrew service or
another database. Credentials are random, private local files; existing env files
are preserved. If setup rejects an existing configuration, inspect it locally;
never paste credentials into chat, logs or Git.

`DATABASE_URL` uses the restricted `learli_app` role. `DATABASE_URL_DIRECT` uses
`learli_owner` for reviewed local migrations/fixture setup. App code cannot grant
roles, update account status, alter schema or delete audit history. Connection
helpers reject remote hosts, URL query overrides and arbitrary database names.
The test wrapper always loads `.env.test.local`; test helpers additionally reject
`learli_dev`. No destructive reset command is supplied.

## Local accounts and messages

- `npm run db:seed` creates the fixed synthetic student, parent, tutor, admin and
  multi-role accounts. It is idempotent and refuses to elevate an existing account
  that does not match its private fixture manifest.
- `npm run fixtures:open` opens their private HTML credential sheet. Never reuse
  those passwords outside local Learli. Fixture verification is trusted setup;
  normal signup still requires following the verification link.
- Sign up at `/sign-up` with a made-up name and a `.test` address. New accounts
  have no roles; a user cannot self-register as admin or approve a tutor.
- `npm run mail:open` opens the latest **development** message in the browser.
  Follow its local verification/reset link. Captures live under `.local/mail/`,
  never a public route; nothing is sent externally. Tests use a separate mailbox.
- Private files are mode 0600 under mode 0700 directories. Treat them as secrets;
  do not publish `.local`, `.env.local`, `.env.test.local`, or auth traces.
- Account settings update only your display name/timezone. Role workspaces are
  guarded shells; guardian links, tutor eligibility and bookings are later work.

Local auth requires `AUTH_MODE=local`, development/test APP_ENV, a loopback HTTP
APP_URL, matching auth origin, a secret and the dedicated database. Staging and
production modes reject it. Default `dev`/`start` bind loopback. This does not
provide a deployable real-user enrollment flow or a production email adapter.

## Schema and verification

```sh
npm run auth:generate   # regenerate provider-owned tables from shared auth options
npm run db:generate    # generate SQL; inspect the diff before applying
npm run db:migrate
npm run db:migrate:test
npm run check
npm run test:integration
npm run build
npx --no-install playwright install chromium
npm run test:e2e
```

Auth schema is generated by the pinned Better Auth CLI (`auth` 1.7.7), not a copied
competing auth model. Application tables are separate. Do not use `drizzle-kit
push` or expose Drizzle Studio. The migration runner only accepts designated
local databases and applies committed SQL with Drizzle's migration journal.
Integration tests clear **only** the isolated `learli_test` fixture data. Run them
before browser tests, not concurrently against that same database.

The prepared CI workflow uses its own disposable PostgreSQL container on the
runner loopback interface; no workflow has been dispatched as part of local work.
No provider credentials are needed. Auth browser tracing is disabled to avoid
capturing session/reset/verification credentials. General UI screenshots remain
ignored local artifacts.

Stop with `npm run db:stop`; data is preserved. Restart with `npm run db:start`.
`npm run db:status` reports the owned cluster's state. A rollback of this local
slice means stopping its processes and retaining data; database deletion or a
schema down-migration needs an explicit, reviewed recovery plan.

Hosted Neon connection/TLS validation, hosted migrations, Resend delivery,
production session configuration, safeguarding approval and deployment all remain
future work. See `docs/decisions/2026-10-11-local-m2.md`.
