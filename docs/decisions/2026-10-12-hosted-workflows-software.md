# Hosted workflow software preparation

Date: 2026-10-12. Status: **AUTHORIZED — build-feature delegation**.
Authority: the repository owner approved proceeding with the eight discussed
work areas, with the orchestrator managing implementation and automated testing.
This records delegated software choices; the owner did not separately inspect
or approve the generated blueprint. Parent blueprint:
`prompts/features/m8-10-hosted-workflows-wave.md`.

The scope is administrator MFA/recovery, hosted database runtime support, HTTPS
authentication, Resend account and booking delivery, learner/guardian admission,
policy-governed booking lifecycle, review publication, and tutor screening with
safeguarding workflows. Existing synthetic local functionality is preserved.
All verification uses isolated synthetic resources. Payments remain deferred.

The orchestrator selects provider-supported TOTP and recovery codes, mandatory
current administrator assurance, exact assigned staff review, pending guardian
requests with explicit authorization/revocation, and separate independent College
Support eligibility. Review software permits one immutable integer 1–5 rating
with bounded optional plain text per eligible logical booking, assigned manual
moderation, publish/withdraw with audit, and an anonymous public author label.
Transactional delivery uses a bounded operator-invoked durable drain; no new
always-on worker or scheduler is introduced. These choices support the existing
marketplace scope and minimize additional data collection and infrastructure.

Policy-dependent features consume narrow versioned policy/evidence records and
default to disabled for real operations. Synthetic readiness records exercise the
same domain services and database constraints without becoming real guardian
proof, tutor screening, lesson commitments, attendance or public social proof.
Historical demo rows and private reviews are never promoted into operational
records. Missing intake authority must deny before collecting child information.
No payment gateway, paid flag, pricing, refund or implied free commercial model
is introduced by this decision.

Actual operating markets, legal notices, age and consent rules, guardian proof,
screening sufficiency, staffed escalation, contractual booking conditions and
real publication policy remain unresolved activation requirements. Automated
tests establish software behavior only. Real provider acceptance, deployment,
live sending and production schema/data operations require their own explicit
authorization. This build request does not authorize commit, merge or push.

Separate worktrees and frozen provider manifests govern imports. Root is the
final shared integration owner and may allocate precise shared hunks within a
builder's own checkout. Migration history 0000–0021 remains immutable; reviewed
forward additions must pass fresh and populated upgrade, effective grant and
protection checks. Independent review and combined PostgreSQL/browser evidence
must identify the exact assembled source before a completion claim.

Root's implementation refinement supersedes the parent's proposed generic R0
module: retain the actual auth runtime and compose feature-owned validated
capabilities alongside it. Add shared types only for concrete consumers that
need them; no generic policy engine or activation-receipt service is required.
Hosted auth owns the necessary structural database/runtime composition while
preserving the existing local factory contract. Ordinary assigned domain work
uses current administrator assurance; the five-minute factor-proof window is
reserved for credential/factor changes. Every domain still rechecks current
session, factor, role and exact task authority after lock waits. Safeguarding
extends existing support reviewer, assignment, grant and history records rather
than introducing a parallel staff/assignment system.

Alternatives rejected: rebuilding the already complete demo features, treating a
guardian checkbox or administrator role as proof, activating real operations
from configuration alone, or leaving isolated modules without working integration.
The principal remaining risk is confusing local technical acceptance with real
operational readiness; reports and runtime provenance must keep them separate.
