# Ordinary local workflow on main

The owner requested one ordinary local app in the primary checkout on local
`main`, replacing the separate private preview. Normal registration and durable
role workflows are required; changing simulation labels alone is insufficient.
Data cleanup is explicitly later. Existing data, history, source and private
configuration remain preserved.

The authorized implementation blueprint is
`prompts/features/m8-03-local-operational-workflow.md`, under build-feature
delegation, not separately inspected blueprint approval. New records use
`local_operation` in the existing engine. Old synthetic/fixture records are never
relabeled or advertised as ordinary inventory. The loopback app uses the owned
`learli_dev` database and restricted application role; automated checks use
separate targets. No cloud/production data, provider configuration or deployment
is changed.

Normal valid emails use Better Auth, current verification/session controls and
owner-private captured messages. No email is delivered through a provider.
Current ownership, guardian/independent learner review, tutor screening, Admin MFA,
exact assignments, atomic booking conflicts and private links remain enforced.
One-time trusted setup grants the exact registered verified Admin identity selected
by the owner. In-app claims replace per-record operator dispatch, and never create
evidence or approvals. Missing staff leaves requests pending.

The coordinator interprets “same flow” narrowly as continuing local no-money
60-minute lessons,30-minute starts,60-minute notice,14-day horizon,10-minute
provisional holds and60-minute change cutoffs. Assigned Admin confirms; assigned
Tutor records completion only after saved end. These are local settings, not
approved commercial/customer terms. No automatic meeting attendance is asserted.

Payments, real email delivery, public review publication, legal market/guardian
requirements and staffed safeguarding retain their separate launch gates. Neither
local operation nor its automated evidence authorizes public launch.

Rollback preserves forward schema and new records, stops only the owned local
app and selects the preserved prior runtime. A restore, destructive cleanup or
production action requires its own authorization. Implementation and check status
are recorded separately in `context/progress-tracker.md`.

Account support retains the existing exact staff/account grant model, so more
than one capable Admin can hold separate revocable access to the same account.
This is an account-support grant, not an exclusive pending review. Admission,
screening, booking and support-case claims still have one assignee. No account
census or additional private learner/meeting access is introduced.
